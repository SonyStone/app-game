# Нативный Paint: прототипы на разных стеках

Передача из треда про hover-баг Chrome (2026-10-14) в новый тред. Документ — источник правды: правь текст, агент приводит работу к нему. Нерешённое помечено «❓», вопросы агента — «❓ (агент)».

## Зачем

1. **Hover пера в Chromium ненадёжен.** На MovinkPad hover пропадает до пересоздания вкладки ([crbug 573236768](https://issues.chromium.org/issues/573236768)). Причину сузили через `apps/android-hover-probe`:
   - то же самое происходит в Android System WebView 153, значит виноват общий код Chromium, а не вкладки Chrome;
   - Android продолжает присылать hover в окно, теряет его уже Chromium;
   - вернуть hover можно только новым экземпляром WebView или вкладки;
   - поломку вызывает окно, перекрывшее приложение (системный выбор файлов, даже открытый из другого приложения), вместе с касанием пера около этого момента. Срабатывает не каждый раз;
   - не регрессия 155: в WebView 153 баг уже есть.

   Без hover не работают курсор кисти и palm rejection.
2. **Задержка.** Пользователи уже жаловались на задержку пера. Обходы, которые её увеличивают, не годятся. Поэтому отклонён мост «hover из APK → синтетические PointerEvent».

Цель: собрать несколько прототипов на разных стеках и сравнить, что лучше работает и как выглядит.

## Прототип (одинаковый для всех стеков)

- Холст на весь экран, рисование одной кистью: **«Kyle's Drawing Box - Animator Pencil 2016»** из Megapack (`~/Downloads/megapack.abr`). Пользователю она нравится больше всех. Сначала проверить точное имя пресета в файле.
- Перо: давление, наклон и hover. Курсор кисти по hover, palm rejection не ломается.
- Минимальный интерфейс. Направление: как можно более «воздушный» и простой (не плотный). Правила кластера: `apps/paint/docs/tile-cluster.md`.
- ❓ Нужны ли в прототипе pan/zoom/rotate, undo, слои?

## Стеки-кандидаты

| Стек | Что переиспользуется | Что проверить |
|---|---|---|
| React Native + `react-native-wgpu` + TypeGPU | движок на TS (`packages/paint-core`), шейдеры TypeGPU | ввод пера в нативном потоке, без JS; задержка; производительность движка в Hermes и worklets |
| Rust + wgpu (интерфейс: egui или другой) | WGSL из TypeGPU (`tgpu.resolve`) | ввод пера через NDK `MotionEvent` (поддержка пера в winit слабая); один код на Android, iPad, десктоп и веб (WASM) |
| Kotlin-оболочка + ядро на Rust/wgpu | WGSL; Gradle-проект `apps/android-hover-probe` как основа | front buffer (`androidx.graphics`, `GLFrontBufferedRenderer`), предсказание движения (`androidx.input`); вызов ядра через JNI |

❓ Добавить ли другие стеки (Flutter, Kotlin + Vulkan напрямую, Swift для iPad)?

Ранее решено: rust-gpu имеет смысл только для приложения под нативный Vulkan, шейдеры остаются на WGSL.

## Как сравнивать

- **Задержка пера:** от касания до штриха на экране. Нужен одинаковый метод для всех стеков, например съёмка slow-motion. ❓ (агент) Какой метод выбрать?
- **Стоимость отпечатка кисти на GPU.** Ориентир — Chrome: примерно 290 мкс на отпечаток в Mixer (`apps/paint/performance/README.md`).
- **Надёжность hover:** сценарии из `apps/android-hover-probe/README.md` (выбор файлов, переключение приложений).
- Внешний вид и ощущение от рисования. Это оценивает пользователь на планшете.

## Что есть под рукой

- Планшет: Wacom MovinkPad Pro 14 (adb `5il21u1000464`), Android 15, Snapdragon 8s Gen 3 / Adreno 735. На Mac есть Android SDK и NDK, JDK 17, Gradle 8.14.3.
- Кисти: в `packages/abr-parser`, `abr-brush`, `abr-paint` есть парсинг ABR и динамика кистей.
- Чтобы не портировать парсер ABR в каждый стек, кисть можно один раз выгрузить в нейтральный формат: JSON с параметрами и PNG с отпечатком.
