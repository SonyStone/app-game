<Section title="Beginner summary">

The important change is architectural. The app is not only gaining features; it is being reorganized so future features can be added without editing one giant controller every time.

An SVG editor has several jobs at once:

- It must store an SVG document.
- It must know what SVG elements and attributes mean.
- It must let the user select objects, path points, handles, and later text ranges or gradient stops.
- It must turn user actions into undoable document changes.
- It must render the document and overlays.
- It must expose panels, menus, shortcuts, settings, diagnostics, and extension packages.

The new architecture separates those jobs. The editor now has a central `EditorKernel`, smaller services, contribution registries, operation-backed commands, typed selection targets, SVG capabilities, viewport tools, renderer boundaries, and package diagnostics.

</Section>

## The current architecture

<SystemMap />

The `EditorKernel` is the main runtime object. It exposes services such as `documents`, `selection`, `commands`, `settings`, `viewport`, `resources`, `capabilities`, `rendering`, `input`, `ui`, and `registries`.

The kernel does not mean everything is centralized in one large file. It means each subsystem has a stable doorway. A panel, shortcut, viewport tool, command palette item, or extension should use the official service instead of reaching into private shell state.

The shell controller is now mostly a **composition root**. Its job is to build the services and wire them together:

1. Load persisted settings.
2. Build contribution registries.
3. Build SVG capability registries.
4. Create document, selection, overlay, file, viewport, workbench, and app host services.
5. Create the kernel.
6. Start shortcut handling.

That is the correct direction. In a mature application, the shell should assemble the app; it should not personally contain every editor behavior.

## Why this architecture is better

<PatternStackDiagram />

The most important idea is **controlled growth**.

A small app can survive with one main component that knows everything: the selected SVG node, the active tool, all toolbar buttons, every command, all sidebar panels, and every SVG attribute rule. That feels productive at first because you can add a feature by opening one file and typing more code.

The problem is that this style gets worse every time the app succeeds. When you add gradients, text editing, path handles, snapping, masks, layers, symbols, plugins, and file import, the same central places keep changing. A bug in one feature can break another feature because they share too much hidden state.

The new architecture is better because it makes each feature answer clear questions:

1. **Where does this feature plug in?** A contribution says whether it adds a command, panel, tool, menu item, shortcut, renderer, setting, or SVG capability.
2. **What service does it need?** A feature asks the kernel for documents, selection, history, viewport, UI, or registry services instead of importing random shell internals.
3. **What document change does it make?** A command creates operation data, not an invisible closure.
4. **What does it know about SVG?** SVG element rules live in capabilities, not scattered switch statements.
5. **How can the app explain failure?** Package diagnostics can say a feature is blocked, disabled, incompatible, missing a dependency, or waiting for migration.

This gives the editor a shape closer to a professional platform. The app can still have built-in features, but built-in features and future extensions use the same path.

That matters because an Illustrator-class app is not just "many tools." It is a system where many tools can coexist without each tool needing to know every other tool.

### What "better" means in practice

Better architecture does not mean more abstract words. It means fewer scary edits later.

If you add a **gradient editor** in a prototype-style app, you might need to edit:

- the sidebar component so it can show gradient controls;
- the toolbar so it can add gradient buttons;
- the command handler so it can create and update gradients;
- the SVG metadata table so gradients are recognized;
- the selection state so gradient stops can be selected;
- the undo code so dragging a stop is one history entry instead of 50 entries;
- the renderer so gradient handles appear on the canvas;
- the import/export path so gradient resources stay valid.

In the new architecture, the gradient feature should mostly arrive as contributions:

```ts title="Gradient feature as contributions"
export const gradientContribution = {
  id: 'core.gradients',
  panels: [gradientPanel],
  commands: [setGradientStopCommand, addGradientStopCommand],
  tools: [gradientStopTool],
  shortcuts: [gradientShortcuts],
  viewportOverlays: [gradientOverlay],
  svg: {
    elements: [linearGradientCapability, radialGradientCapability, stopCapability],
    attributeControls: [gradientStopColorControl, gradientStopOffsetControl],
    resourceReferences: [paintServerReference]
  }
} satisfies EditorContribution;
```

The editor still needs real implementation work, but the work has a home. The gradient panel goes into `panels`, the gradient stop tool goes into `tools`, the SVG rules go into `svg`, and document changes become commands with operations.

That is the difference between **adding code to a pile** and **adding a feature to a platform**.

## Why these patterns fit an SVG editor

SVG editing has several hard qualities at the same time.

It is a **document editor** because the SVG tree is the source of truth.

It is a **graphics editor** because users manipulate shapes visually with pointers, handles, snapping, rulers, and overlays.

It is a **code editor** because the SVG can be viewed and edited as source text.

It is a **plugin host** because professional users eventually need custom tools, custom panels, custom importers, and domain-specific objects.

It is a **history machine** because almost every visible change must support undo, redo, merging, and sometimes replay.

No single simple pattern covers all of that. That is why the architecture uses a stack of patterns:

- **Kernel services** keep the core editor jobs reachable through stable APIs.
- **Contribution registries** make UI and tools discoverable instead of hard-coded.
- **Operation-backed commands** make edits inspectable, undoable, and testable.
- **Typed selection targets** let the editor select more than whole SVG nodes.
- **SVG capabilities** keep SVG knowledge near the feature that owns it.
- **Package lifecycle diagnostics** make extension loading explainable.
- **Renderer boundaries** let the app improve rendering later without changing every command.

Each pattern is there because SVG editors naturally grow in that direction. Without these boundaries, the app would keep adding special cases until nobody is confident changing it.

## Alternatives and tradeoffs

<ArchitectureAlternatives />

The chosen direction is a **kernel plus contributions** architecture.

That does not mean every feature must be external or complicated. It means the app should behave as if features could become extensions later. Core features can still ship inside the app, but they should register through the same surfaces future packages will use.

This is a good middle path:

- It is more structured than a prototype shell.
- It is less heavy than making every internal feature a separately downloaded plugin today.
- It preserves the SVG document model instead of forcing everything into a generic scene graph.
- It borrows the useful part of event sourcing - edits as data - without requiring a full event store immediately.
- It leaves room for a better renderer later because rendering is not the architecture center.

The cost is real. This architecture has more names and more files. A beginner has to learn concepts like kernel, registry, contribution, capability, operation, adapter, and diagnostic. The benefit is that each concept protects the app from a specific kind of future mess.

If the editor were only a weekend SVG toy, this would be too much. For an Illustrator-class foundation, it is the kind of structure that lets the project keep growing.

## How an edit works

<ActionFlowDiagram />

The strongest improvement is the move from opaque command functions toward operation-backed commands.

Old style command:

```ts title="Old mental model"
const command = {
  id: 'svg.delete',
  label: 'Delete',
  apply(root) {
    return removeNode(root, selectedNodeId);
  }
};
```

This works, but it is hard to inspect. History can store the final result, but the command itself is just a JavaScript closure.

New style command:

```ts title="Operation-backed command"
const command = createOperationCommand({
  id: 'svg.set-fill',
  label: 'Set fill',
  mergeKey: `svg.set-fill:${nodeId}`,
  operations: [
    {
      kind: 'svg.set-attribute',
      nodeId,
      name: 'fill',
      value: '#2f7d65'
    }
  ]
});
```

This is better because the edit is plain data. Plain data can be tested, logged, inverted for undo, merged during drags, replayed later, serialized for plugin safety, and eventually sent across a collaboration channel.

## Contributions and registries

A contribution is a bundle of things that a feature adds to the editor. Core editor features use the same contribution path that future extensions should use.

```ts title="Contribution shape"
export const shapeToolContribution = {
  id: 'example.shape-tool',
  tools: [
    {
      id: 'example.rectangle-tool',
      label: 'Rectangle tool',
      priority: 40,
      createTool: (context) => createRectangleTool(context)
    }
  ],
  commands: [
    {
      id: 'example.insert-rectangle',
      label: 'Insert rectangle',
      durability: { kind: 'operation' },
      createOperations: () => [
        {
          kind: 'svg.insert-node',
          parentId: toSvgNodeId('root'),
          index: 0,
          node: createElementNode('rect', [
            { name: 'x', value: '24' },
            { name: 'y', value: '24' },
            { name: 'width', value: '120' },
            { name: 'height', value: '80' }
          ])
        }
      ]
    }
  ]
} satisfies EditorContribution;
```

The registry builder takes installed contributions and projects them into lists:

- `actions`
- `commands`
- `tools`
- `panels`
- `viewportToolbars`
- `viewportOverlays`
- `viewportLayers`
- `shortcuts`
- `appMenus`
- `modals`
- `settingsSections`
- `contextMenus`
- `svg`
- `renderers`

This is what makes the app extensible. The sidebar does not need to know every panel ahead of time. The command palette does not need a hard-coded list of every command. The settings modal does not need a switch statement for every future package. They read registries.

## Package lifecycle

<PackageLifecycleDiagram />

The package system is now more than a flat plugin list. Packages have manifests, dependencies, API versions, migrations, update metadata, activation states, load order, diagnostics, and provenance.

```ts title="Package manifest example"
export const samplePackage = {
  manifest: {
    id: 'sample.extension-package',
    name: 'Sample Extension',
    version: '0.1.0',
    editorApiVersion: currentEditorExtensionApiVersion,
    dependencies: [
      { id: 'core.svg-shapes', version: '1.0.0' }
    ],
    migrations: [
      {
        id: 'api-1-shape-defaults',
        fromEditorApiVersion: 0,
        toEditorApiVersion: 1,
        description: 'Update shape defaults for the editor API 1 contract.'
      }
    ],
    description: 'Reference package for extension surfaces.'
  },
  contributions: [sampleExtensionContribution]
} satisfies EditorExtensionPackage;
```

The package host can now explain package state:

- `active`: the package is valid and its contributions are installed.
- `disabled`: the user or host policy disabled it.
- `blocked`: the package has a problem, such as invalid metadata, missing dependencies, incompatible API version, dependency cycle, or unapplied migration.

This is important for a serious editor. A professional extension system must be debuggable. If a package cannot load, the app should explain why instead of silently failing.

## SVG capability model

The SVG capability registry is where the editor learns what SVG means.

Before this architecture, SVG knowledge was too scattered. A single element might require changes in metadata tables, add menus, inspector controls, handles, validation, resource references, rendering, and tests.

Now a capability can describe those things together:

```ts title="SVG capability example"
const badgeElement = {
  name: 'sampleBadge',
  defaults: {
    x: '24',
    y: '24',
    width: '96',
    height: '40',
    tone: 'info'
  },
  allowedChildren: [],
  attributes: ['x', 'y', 'width', 'height', 'tone', 'sample-token'],
  addable: true,
  addableOrder: -100,
  createNode: () =>
    createElementNode('sampleBadge', [
      { name: 'x', value: '24' },
      { name: 'y', value: '24' },
      { name: 'width', value: '96' },
      { name: 'height', value: '40' },
      { name: 'tone', value: 'info' }
    ]),
  getBounds: ({ node }) => ({
    x: numericAttribute(node, 'x', 0),
    y: numericAttribute(node, 'y', 0),
    width: numericAttribute(node, 'width', 0),
    height: numericAttribute(node, 'height', 0)
  }),
  validate: (node) => validateBadgeTone(node)
} satisfies SvgElementContribution;
```

That means one feature can bring its own element defaults, add-menu support, inspector metadata, bounds, handles, resource references, and diagnostics.

## Typed selection

Professional editors do not only select whole objects. They select path points, handles, text ranges, gradient stops, artboards, guides, symbols, masks, and isolated subtrees.

The old model was mostly selected node IDs. The new model uses `SelectionTarget`.

```ts title="Selection target examples"
type SelectionTarget =
  | { readonly kind: 'node'; readonly nodeId: string }
  | { readonly kind: 'path-command'; readonly nodeId: string; readonly index: number }
  | {
      readonly kind: 'path-anchor';
      readonly nodeId: string;
      readonly commandIndex: number;
      readonly parameter: string;
    };

const selectedRectangle = nodeSelectionTarget('rect-1');
const selectedPathPoint = pathAnchorSelectionTarget('path-1', 4, 'x');
```

This prevents the codebase from growing one special selection variable for every new editing mode. The model can grow in a controlled way.

## Where to read more

Read these in this order if the architecture still feels abstract.

### Beginner path

1. [Inversion of Control Containers and the Dependency Injection pattern](https://martinfowler.com/articles/injection.html) by Martin Fowler. This explains why code often asks another object for services instead of constructing everything itself.
2. [Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture) by Alistair Cockburn. This is the classic explanation of ports and adapters: keep the core app separate from UI, databases, files, renderers, and other outside systems.
3. [Redux Fundamentals: State, Actions, and Reducers](https://redux.js.org/tutorials/fundamentals/part-3-state-actions-reducers). This is useful for understanding why "describe the change as data" is easier to reason about than "call a function that does unknown things."
4. [Redux Immutable Update Patterns](https://redux.js.org/usage/structuring-reducers/immutable-update-patterns). This helps with the SVG tree side of the editor, because many document edits should create a new tree instead of mutating random old objects.
5. [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) by Martin Fowler. Read this later. The editor is not fully event-sourced today, but operation-backed commands borrow the important idea that state changes can be represented as explicit objects.

### Software examples to study

1. [Visual Studio Code Extension API](https://code.visualstudio.com/api). VS Code is a strong example of an app where built-in and external features use extension-style contribution points.
2. [VS Code Extension Samples](https://github.com/microsoft/vscode-extension-samples). These examples show how commands, menus, views, language features, and other extension surfaces are shaped in a real product ecosystem.
3. [Figma Plugin API](https://developers.figma.com/docs/plugins/). Figma is useful to study because plugins can inspect and change design documents through a controlled API.
4. [ProseMirror Guide](https://prosemirror.net/docs/guide/). ProseMirror is for rich text, not SVG, but it is excellent for learning how a serious editor separates document model, state, transactions, plugins, and views.
5. [Lexical Introduction](https://lexical.dev/docs/intro) and [Lexical Commands](https://lexical.dev/docs/concepts/commands). Lexical is another editor architecture worth studying because it treats commands and extensions as first-class concepts.

### Books

1. [Working Effectively with Legacy Code](https://www.informit.com/store/working-effectively-with-legacy-code-9780131177055) by Michael Feathers. This is the most practical book for improving a real existing codebase without breaking it.
2. [Patterns of Enterprise Application Architecture](https://martinfowler.com/books/eaa.html) by Martin Fowler. This is useful for learning architecture vocabulary and why patterns exist.
3. [Design Patterns: Elements of Reusable Object-Oriented Software](https://dl.acm.org/doi/10.5555/186897) by Gamma, Helm, Johnson, and Vlissides. This is the classic pattern book. It is dry, but many terms people use still come from it.
4. [Clean Architecture](https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/) by Robert C. Martin. Read this critically. The useful part here is dependency direction: important business/editor rules should not depend on accidental UI details.

When reading, do not try to memorize pattern names first. Ask four simpler questions:

1. What is the source of truth?
2. What changes together?
3. What can be tested without opening the whole app?
4. Which direction do dependencies point?

If you can answer those questions, the architecture will start to feel much less mysterious.

## How to judge future work

When adding a new feature, use this checklist:

1. Does it register through a contribution when possible?
2. Does it use the kernel service boundary instead of reaching into shell internals?
3. Does a document edit become an operation-backed command?
4. Does selection use `SelectionTarget` instead of inventing a new global state field?
5. Does SVG knowledge belong in a capability contribution?
6. Does the viewport behavior belong in a tool?
7. Does the UI read a registry instead of hard-coding the feature list?
8. Does the package host get diagnostics if the feature comes from an extension?
9. Is there a focused test for the behavior?
10. Can the next developer understand where this feature plugs in?

If the answer is usually yes, the editor is moving toward a professional foundation. If the answer is no, the app is drifting back toward prototype architecture.
