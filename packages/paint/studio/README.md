# Paint Studio

Рабочая первая версия редактора находится на `/paint/studio`. Старые эксперименты остаются в `/paint`.

[Руководство по сопровождению](./MAINTENANCE.md): карта модулей, контракты ошибок, ограничения очередей и необходимые проверки.

## Возможности

- Растровый холст с разреженными тайлами 256×256 и отрицательными координатами.
- Мягкая круглая кисть, ластик, размер, hardness, независимые flow и opacity целого мазка.
- Давление пера отдельно управляет размером и flow. Мышь использует давление 1.
- Слои, видимость, порядок, непрозрачность, Smooth color / Normal (classic) / Multiply / Screen / Overlay.
- Холст занимает всё окно. Компактные плавающие инструменты используют стиль `/grease-pencil-typegpu`; настройки кисти, цвета, слоёв и файлов открываются по запросу. На телефонах панели располагаются снизу, в низком окне прокручиваются.
- Кнопка рядом с масштабом включает полный экран для всего редактора. Состояние обновляется и при выходе через Escape; отказ браузера показывается сообщением.
- Undo/redo по точным снимкам изменённых тайлов, включая изменения слоёв.
- Lasso выделяет пиксели активного слоя: перемещение, Copy/Cut/Paste, удаление и перенос в новый слой одной записью undo.
- Pan, zoom, rotate и зеркальное отображение камеры. Puck вызывается удержанием Space, клавишей V или правой кнопкой.
- Автосохранение завершённых действий в IndexedDB, восстановление после перезагрузки, импорт/экспорт `.paint`.
- Drawing menu → Canvas wireframe показывает исходные тайлы, выбранные обзорные страницы и их треугольники. Зелёные страницы резидентны, жёлтые используют грубый fallback, розовые загружаются. Статистика включает LOD, draw calls, RAM/GPU-кэши и чтения/записи тайлов. Overlay учитывает pan/zoom/rotate/mirror и текущий мазок, не попадает в PNG или файл проекта.
- PNG экспортирует текущий вид холста с фоном. Это не экспорт всего бесконечного документа.
- Потеря GPU-устройства приостанавливает рисование. Кнопка восстановления создаёт новое устройство из версионных тайлов завершённых мазков в RAM/IndexedDB.

## Управление

| Действие               | Управление                                  |
| ---------------------- | ------------------------------------------- |
| Рисовать               | Перо или левая кнопка мыши                  |
| Переместить вид        | Зона Pan в Puck, средняя кнопка или один палец |
| Масштаб и поворот      | Два пальца                                  |
| Масштаб                | Колесо, кнопки сверху или puck              |
| Puck                   | Удерживать Space, V, правая кнопка или кнопка справа внизу |
| Кисть / ластик         | B / E                                       |
| Lasso                 | L                                           |
| Копировать / вырезать / вставить выделение | Ctrl или Cmd + C / X / V, когда выбран Lasso |
| Снять выделение       | Escape или Ctrl/Cmd + D                     |
| Удалить выделенные пиксели | Delete / Backspace, когда выбран Lasso   |
| Размер кисти           | [ / ]                                       |
| Отмена / повтор        | Ctrl или Cmd + Z / Shift + Z                |
| Сохранить файл         | Ctrl или Cmd + S                            |
| Отменить текущий мазок | Escape                                      |

Касания во время рисования пером игнорируются. Это простое подавление случайных касаний ладонью, а не классификатор контактов планшета.

Lasso замыкается при отпускании пера или мыши. Потяните внутри контура, чтобы переместить выделенные пиксели; снаружи начинается новое выделение. Во время перемещения движется контур, пиксели записываются при отпускании с округлением до целого пикселя документа. Zoom, rotate и mirror учитываются. Касания по-прежнему управляют камерой.

Copy/Cut/Paste используют внутренний буфер текущего редактора. Paste вставляет в активный слой в исходных координатах скопированных пикселей; затем результат можно переместить. Для копирования в отдельный слой нажмите Copy, создайте слой в Layers и нажмите Paste. Move to new layer переносит пиксели в новый слой над исходным, сохраняет opacity и blend слоя и выбирает новый слой. Весь перенос отменяется одним Undo. Буфер и контур не сохраняются после перезагрузки. Контур снимается при рисовании, смене инструмента, изменении слоёв, undo/redo и импорте. Выделение не ограничивает последующее рисование кистью.

Первая версия использует чёткую границу по центрам пикселей, без feathering и сложения выделений. Лимита в 256 тайлов больше нет. Выделение и результат обрабатываются по одному тайлу; готовые версии записываются в IndexedDB партиями около 8 MiB без замены текущего checkpoint. В RAM остаются ограниченный кэш и текущий тайл, поэтому временная память не растёт с площадью выделения. Ошибка диска до commit не меняет рисунок.

Puck использует векторную версию предоставленного пользователем изображения (`packages/navigation-puck/src/assets/navigation-puck.svg`); исходный PNG сохранён рядом как образец: синее кольцо поворачивает вид, центр перемещает, нижняя секция меняет масштаб. UI, контроллер и обработчики ввода находятся в общем пакете `@app-game/navigation-puck`: Puck скрывается на время жеста, zoom реагирует только на вертикальное перемещение, масштабирование и поворот используют центр viewport. При разовом вызове Puck закрывается после операции. При удержании Space он снова появляется в точке отпускания; отпускание Space посреди жеста позволяет завершить жест. Правый drag выбирает изображённую зону после 30 px движения, при выборе правым drag вокруг центра действует мёртвая зона 12 px; прямое нажатие на кнопку начинает жест сразу. Shift фиксирует поворот с шагом 15°. Зоны также поддерживают стрелки клавиатуры; крестик закрывает Puck. Панели закрываются крестиком, нажатием снаружи или Escape.

## Устройство

`PaintStudio.tsx` собирает интерфейс из `BrushPanel`, `LayersPanel` и общего `NavigationPuck`. `paintNavigation.ts` адаптирует общие жесты к 2D-камере Paint. `createPaintSession.ts` управляет worker и DOM-слушателями. `input.ts` получает Pointer Events, сохраняет coalesced samples с их давлением и отправляет один пакет за animation frame. Перед `end` ожидающие samples отправляются обязательно.

Первый sample отправляется синхронно на `pointerdown`. Worker растеризует и показывает его внутри команды `begin`, до следующей команды в очереди. Иначе быстрый `end` может начать readback и подготовку обзоров раньше отложенного кадра. Движение остаётся пакетным. `workerLatency.test.ts` проверяет порядок первого показа при немедленном отпускании пера и заблокированном readback; это проверка очереди, а не измерение задержки физического стилуса.

В secure context с поддержкой `pointerrawupdate` перо передаёт реальные coalesced samples через raw-события. После первого raw-события в мазке соответствующие `pointermove` не подаются в фильтр повторно. Если raw-события не приходят, продолжает работать `pointermove`. Кольцо пера скрывается во время рисования, но остаётся при наведении; мышь сохраняет курсор.

В меню Drawing → Developer находятся Canvas wireframe, Live stroke tail и Show cursor while drawing with a pen. Окно различает обнаруженную поддержку `pointerrawupdate` и фактически полученные raw-события, показывает объём GPU-ресурсов и время подготовки/отправки последнего кадра. Это не измеритель задержки пера. Переключатели действуют до перезагрузки страницы.

`preview()` у сглаживателя вычисляет временные отпечатки до последней реальной точки, не сдвигая историю давления и шаг кисти. Renderer смешивает их с копией базы и накопленной маски в отдельном пуле до восьми тайлов. Старый хвост удаляется при обновлении, отключении, cancel и finish. Он не входит в readback, undo, экспорт или сохранённые обзоры. Финальная кривая и настройки catch-up сохраняют прежнее поведение; предсказанные браузером точки пока не используются. `Check live stroke tail` сравнивает пиксели с обычной растеризацией кисти и ластика, в том числе через virtual texture и вытеснение scratch-тайлов.

`createSelection.ts` хранит временный контур в координатах документа, `SelectionActions.tsx` показывает команды. Контур передаётся worker отдельным сообщением `selection-view`, которое объединяется с текущим состоянием. `gpu/lassoOverlay.ts` переносит алгоритм lasso-примера в TypeGPU: triangle fan разворачивается в triangle list, stencil parity задаёт even-odd заливку в R8-маске, затем edge shader рисует движущиеся диагональные штрихи. Проходы используют существующие root, GPUDevice и GPUCanvasContext Paint Studio. Отдельного canvas или SVG нет. Маска обновляется только при изменении контура или камеры; анимация перерисовывает представление из кэша с частотой до 30 кадров/с, не растеризуя слои заново. Контур не попадает в тайлы, кэш рисунка или PNG. При скрытой вкладке и reduced motion анимация останавливается.

`selection.ts` читает занятые тайлы области, использует even-odd маску по центрам пикселей и подготавливает неизменяемые версии. Для каждой целевой плитки сначала удаляются исходные выбранные пиксели, затем накладываются части максимум четырёх выбранных тайлов premultiplied sRGB source-over. Это сохраняет перекрывающиеся перемещения и ограничивает память. Буфер обмена хранит версии тайлов в IndexedDB и включён в живые ссылки сборщика. `document.commit` записывает новый слой вместе с пикселями одной атомарной операцией. После commit используются обычные сброс GPU-кэша, подготовка обзоров и автосохранение.

Worker содержит Solid root для жизненного цикла, модель документа и GPU renderer. `brush.ts` размещает отпечатки по длине пути, сохраняя остаток шага между пакетами. JSX используется для крупных модулей интерфейса; отдельные отпечатки представлены массивами, а не реактивными компонентами.

Каждый затронутый тайл имеет исходное изображение, маску мазка и отдельный результат. Эти GPU-текстуры переиспользуются, пока тайл находится в кэше. Новый мазок копирует исходное изображение и очищает маску на GPU. Маска накапливает flow аппаратным source-over blending. Шейдер смешивает исходное изображение с маской, применяя opacity один раз ко всему мазку. Ластик использует destination-out. На завершении только затронутые тайлы читаются в CPU и становятся одной записью истории. Резидентные тайлы читаются одной отправкой копирования и одним mapAsync, без последовательного ожидания каждого тайла.

Тайлы хранят premultiplied RGBA8 в sRGB. Режим Smooth color декодирует цвета в линейный RGB, выполняет source-over и кодирует результат обратно в premultiplied sRGB. Кисть и слои используют общую TypeGPU-функцию `gpu/colorMixing.ts` с [передаточной функцией sRGB из W3C](https://www.w3.org/TR/css-color-4/#color-conversion-code). Режим включён по умолчанию для кисти и новых слоёв. Это устраняет провал яркости при смешивании красного с зелёным; это не физическая модель пигментов.

Существующие файлы сохраняют выбранные режимы. Для старого слоя можно выбрать Smooth color в панели Layers. Multiply продолжает затемнять цвет согласно своему назначению. Уже записанные в растровые тайлы тёмные пересечения старых мазков не пересчитываются. ICC, HDR и 16-bit painting пока не реализованы.

Камера не изменяет пиксели. В GPU передаются смещения тайлов относительно центра камеры, чтобы сохранять точность далеко от начала координат. Рендерер отсекает невидимые тайлы и группирует их в render passes. Mipmaps обновляются только при уменьшении изображения, когда они нужны для выборки. Слои смешиваются через две текстуры размером с viewport и промежуточную текстуру слоя. Четвёртая текстура сохраняет готовый вид: при рисовании пересчитывается лишь экранная область изменённых тайлов, включая все слои в этой области. Навигация, изменения слоёв, undo/redo и отмена мазка инвалидируют вид. Очистка выполняется через render-pass loadOp, без массивов нулей в CPU. В простое новые кадры не отправляются. Worker ожидает завершения GPU-кадра перед следующим запланированным кадром и объединяет поступившие изменения камеры, чтобы очередь отрисовки не накапливалась.

## Виртуальные страницы и хранение

`tileStore.ts` хранит неизменяемые версии тайлов отдельными записями IndexedDB. Модель документа и undo/redo ссылаются на версии, поэтому все пиксели рисунка не обязаны оставаться в RAM. Автосохранение записывает только новые версии плюс метаданные документа в одной транзакции; поворот камеры не переписывает пиксели. Чистый LRU-кэш ограничен 64 MiB. Несохранённые версии закреплены до успешной записи, поэтому большой мазок временно может превысить этот бюджет. Сборщик удаляет версии, которые больше не нужны текущему checkpoint и живой истории. Старые checkpoint мигрируют при следующем сохранении.

`virtualPages.ts` строит разреженную пирамиду уровней 0–12: каждый родитель объединяет четыре дочерних тайла в одну страницу 256×256. Изменение исходного тайла инвалидирует его родителей и границы соседей. Производные пиксели занимают до 16 MiB RAM-кэша и сохраняются в IndexedDB вместе с исходными тайлами. Ключ каждой страницы — SHA-256 от версии фильтра, уровня и четырёх дочерних версий. Проверка ключа читает метаданные; для открытия готового low-res не требуется декодировать high-res. После изменения тайла пересчитывается только его ветка пирамиды, неизменившиеся дочерние обзоры берутся с диска. Undo может повторно использовать ранее сохранённую версию.

Перед завершением мазка, восстановлением документа и изменением слоёв `prepareOverview` обновляет и загружает текущий обзор в GPU. Поэтому zoom-out после близкого рисования использует уже обновлённый low-res. Автосохранение публикует метаданные документа и подготовленные страницы в одной транзакции; большие партии предварительно записываются без замены checkpoint. Незаписанные обзорные данные сбрасываются партиями около 8 MiB. Старые производные версии ограничены дисковым бюджетом 256 MiB; текущие закреплённые корневые обзоры защищены от удаления. Исходные пиксели и история очищаются отдельно.

Существующим рисункам без low-res нужна однократная подготовка при первом открытии после обновления. После неё обзор сохраняется и следующие открытия используют готовые страницы. Дисковый формат IndexedDB мигрирует с версии 2 на 3 с сохранением исходных тайлов. Бинарный `.paint` пока переносит исходные тайлы; после его импорта обзор строится и сохраняется один раз.

`gpu/virtualTexture.ts` выбирает занятые страницы по viewport и масштабу на CPU. Их размещение в общей `texture_2d_array` ограничено 256 слотами (около 65 MiB); страница содержит 256×256 пикселей и рамку шириной один пиксель из настоящих соседей. Это исключает фильтрацию между посторонними слотами и швы на границах страниц. Один instanced draw рисует страницы одного слоя. Два фоновых задания загружают видимые страницы и заранее готовят небольшой обзор всего слоя. Пока видимые детали загружаются, один слот загрузки может строить обзор; он не отменяется движением камеры. Обзор закреплён в GPU-пуле и не вытесняется навигацией. При приближении доступны родительские страницы, при отдалении сохраняются дочерние. Пересекающиеся уровни рисуются однократно, чтобы прозрачность не удваивалась. Новый родитель может атомарно занять слот своего дочернего тайла, даже когда предыдущий вид использует весь пул.

`gpu/viewFallback.ts` временно перепроецирует последний полный кадр при холодном переходе между масштабами. Снимок создаётся на GPU только при необходимости, получает mipmaps и следует pan/zoom/rotate/mirror/resize. Изображение внутри прежнего viewport остаётся видимым, новые области снаружи заполняются загружаемыми страницами. После подготовки нового уровня временная текстура освобождается. При максимальном viewport она занимает около 43 MiB дополнительно; обычные прогретые кадры её не копируют. Это временный вид, он не изменяет документ и не используется в точном PNG-экспорте. Холодное открытие читает сохранённый low-res; построение первого обзора требуется при миграции старого рисунка или импорте файла без обзорных страниц.

Это программная virtual texturing для 2D: таблица резидентности и выбор страниц находятся на CPU, пиксели и выборка — на GPU. Отдельный GPU feedback pass для прямого отображения 2D viewport не нужен. Использованы принципы [Virtual Textures](https://discourse.threejs.org/t/virtual-textures/53353) и [исследования virtual texturing](https://publications.lib.chalmers.se/records/fulltext/155126.pdf), а не Three.js runtime. Из исследования бесконечного холста взяты разреженное хранение и иерархия обзоров. Закрытый алгоритм Leonardo не воспроизводится: отложенная растеризация мазка через независимый preview пока не реализована, кисть по-прежнему записывает полное разрешение.

`paintFile.ts` экспортирует `.paint` с заголовком `PAINT3` и отдельными бинарными payload тайлов. Импорт читает по тайлу и записывает партии около 8 MiB, не заменяя текущий документ до полной проверки файла. Экспорт собирает Blob из отдельных payload без общего base64-буфера. Браузер управляет хранением итогового Blob. JSON-файлы версий 1 и 2 продолжают открываться; внутренние ссылки IndexedDB не принимаются как внешний файл. PNG всегда ожидает полное отображение исходных пикселей выбранного вида.

## Текущие пределы

- Нужны WebGPU и IndexedDB; режим Worker также требует OffscreenCanvas. Автоматического WebGL2 fallback пока нет.
- Документ ограничен 65 536 занятыми тайлами и 128 слоями, доступным местом в браузерном хранилище и ресурсами устройства. Прежний предел 256 MiB снят для рабочего paged-документа и нового бинарного файла. Старый JSON-загрузчик сохраняет защитный лимит 256 MiB.
- Undo/redo хранит до 100 действий с бюджетом версий 1 GiB; последнее действие сохраняется даже при превышении бюджета. История не переносится между перезагрузками. Незавершённый мазок не входит в checkpoint.
- Кэш рисования содержит до 128 исходных тайлов со вспомогательными текстурами. Маски и результаты вытесненных тайлов текущего мазка могут потреблять дополнительную CPU-память до его завершения.
- При рисовании, точном PNG-экспорте и более чем 24 видимых слоях используется точный рендерер с отдельным display cache до 96 MiB. Это обеспечивает корректность при превышении вместимости общего пула, но может быть медленнее обзора через виртуальные страницы.
- Viewport ограничен DPR 2, лимитом GPU-текстуры и примерно 8 мегапикселями. Экранные промежуточные текстуры расходуют память дополнительно к показанным GPU caches; разрешение документа от viewport не зависит.
- Обзорные страницы RGBA8 используют box-фильтр premultiplied-каналов. Это приближённый вид при отдалении; оригинальные пиксели, история и файлы не меняются. Холодный переход в ранее не показанную область может потребовать построения обзора.
- Нет выделений, масок слоёв, фильтров, текстурных кистей, PSD, ICC или совместного редактирования.

## Непрерывность ввода и автосохранение

Шаг отпечатков рассчитывается от фактического диаметра с учётом давления пера. Раньше шаг оставался равным доле полного размера кисти, поэтому тонкий мазок при слабом нажиме распадался на точки. Sampler переносит между событиями оставшуюся долю интервала; для линейного изменения давления интегрирует обратный шаг, отдельно учитывая минимальный диаметр. Это сохраняет расположение отпечатков при разбиении одного движения на большее число событий. Минимальный шаг 0.05 пикселя позволяет перекрывать даже субпиксельные кончики; стационарный ввод не добавляет повторные отпечатки.

`Check stylus pressure` проверяет реальные GPU-пиксели кистей 32/128/512 px при давлении 4% и нарастающем/спадающем нажиме. Проверяются непрерывность, равномерность плотности и opacity при переходах через три границы тайлов с рабочим кэшем на два тайла. Изменение действует на новые мазки; существующий растр не пересчитывается.

`smoothStroke.ts` выбирает обработку мазка по настройке Stroke smoothing в панели кисти. Studio сохраняет прежние квадратичные кривые через середины соседних сегментов и порог входных точек 2 CSS-пикселя с учётом масштаба. Режимы Leonardo описаны ниже. После разбиения кривой существующий sampler расставляет отпечатки по длине дуги и интерполирует давление. Последний сегмент дописывается при завершении. Настройки фиксируются в начале мазка; сохранённые растровые пиксели не изменяются.

### Проба стабилизации Leonardo

В панели кисти выбрать **Stroke smoothing → Leonardo normal** или **Leonardo smooth**. Normal начинается со Stabilization 1, Smooth с 10; значения сохраняются раздельно до закрытия страницы. Studio остаётся режимом по умолчанию. При перезагрузке параметры кисти сбрасываются, как и раньше.

`leonardoStroke.ts` усредняет последние `N = clamp(setting + 1, 1, 50)` сэмплов позиции, исходного давления и времени. История заполняется первой точкой; порог расстояния Studio здесь не применяется. Калибровка выполняется после усреднения: `clamp((pressure - minimum) / (maximum - minimum), 0, 1) ** firmness`. Начальные minimum/maximum: 5%/80%, firmness: 100%, то есть показатель степени 1. Давление мыши остаётся полным. Нормализация гарантирует возрастающий диапазон и положительный показатель степени.

Normal всегда догоняет конец при отпускании пера. В Smooth это регулирует **Catch up on pen lift**. Догоняние синхронно повторяет последнюю точку `N` раз, включая последнее контактное давление. Нулевое давление события pointerup не создаёт искусственное сужение; при неподвижном отпускании дополнительный входной сэмпл не добавляется. При выключенном догонянии линия заканчивается в последней отфильтрованной точке.

`cubicStroke.ts` строит uniform Catmull–Rom с ожиданием одной следующей точки, повтором первой точки для начальной касательной и экстраполированной опорой для последней. Разбиение ограничивает ошибку положения и давления; давление ограничивается диапазоном 0–1. Совпадающие позиции обновляют давление без петли и дополнительного отпечатка. Кубическая кривая может выходить за углы ломаной. Сильная стабилизация добавляет задержку, зависящую от частоты сэмплов. Predicted events не используются.

Основание: локальное исследование `leonardo-analysis/stylus-and-stabilization.md`, 2026-09-06, Leonardo 0.17.70. Воспроизведены исследованные фильтр, калибровка и кубический полином. Расстановка отпечатков и GPU-растеризация остаются реализацией Paint Studio; полного совпадения с Leonardo и задержки настоящего пера эти проверки не устанавливают. Круглая кисть пока не использует наклон и поворот пера.

`leonardoStroke.test.ts` и `cubicStroke.test.ts` проверяют все 50 окон, порядок калибровки, независимость пакетирования, окончания и полином. **Check stylus pressure** на QA-странице проверяет непрерывность GPU-пикселей во всех трёх режимах для кистей 32/128/512 px.

Потеря pointer capture или pointercancel завершает мазок с уже полученными точками. Запоздавшая потеря захвата от предыдущего мазка игнорируется, если новый мазок уже захватил указатель. Автосохранение снимает checkpoint между командами worker; сама запись остаётся фоновой. Список сохранённых ключей low-res позволяет пропустить заведомо отсутствующую новую страницу, не ожидая чтения за незавершённой записью IndexedDB. Внутренние пиксели соседнего тайла сохраняются в кэше при изменении его рамки.

`Run worker checks` удерживает настоящую блокировку записи IndexedDB, запускает debounce автосохранения и рисует восемь мазков. Проверяются пиксели до освобождения блокировки, идентичность файла после сохранения и после запуска нового worker. Unit-тесты проверяют потерю захвата, независимость кривой от пакетирования событий, форму угла, завершение короткого мазка и сглаживание при 5%/100%.

## Большая кисть и длинные активные мазки

Отображение вытесненного участка активного мазка использует его сохранённый output через display cache. Маска и исходные пиксели возвращаются в рабочий GPU-кэш только при повторном рисовании по этому участку. Вытеснение рабочих тайлов выполняет один readback на небольшую LRU-группу, сохраняя маску и output каждого тайла. Лимит рабочих тайлов остаётся 128. Круглая кисть проверяет пересечение диска с тайлом, исключая пустые углы bounding box.

Display cache проверяет неизменяемую версию тайла до чтения IndexedDB. Повторный показ резидентных текстур не загружает исходные пиксели заново. Worker повторно использует статистику завершённого документа до изменения revision; списки отладочных тайлов и страниц отправляются не чаще 10 раз в секунду, кроме явного включения отладки. Камера по-прежнему перемещает сетку локально.

`Check 512px brush` создаёт активный мазок больше рабочего кэша, принудительно перерисовывает его четыре раза и считает реальные GPU mapAsync. Проверяет нулевые readback при показе мазка, сохранность прозрачности при возвращении к вытесненному участку и отсутствие повторного чтения исходных версий после прогрева display cache. На локальном замере четыре полные перерисовки при 5% сократились с 1422 мс / 1320 mapAsync до примерно 101 мс / 0 mapAsync; это синтетический сценарий на одной машине, включая первое заполнение display cache.

## Качество обзорных страниц

Выбор LOD обходит только занятые ветки пирамиды внутри viewport. Пустые ячейки вокруг рисунка не расходуют бюджет и не снижают детализацию при увеличении окна. GPU-пул остаётся на 256 страниц: после резервирования фактического числа закреплённых обзоров остальные слоты делятся между видимыми слоями. Если занятые страницы не помещаются, выбирается более грубый уровень.

Шейдер уменьшенных страниц усредняет четыре bilinear-выборки по размеру экранного пикселя; при увеличении остаётся одна выборка. Это снижает рябь тонких линий между уровнями пирамиды без дополнительных mip-текстур. Смещения ограничены существующей рамкой страницы. Сохранённые исходные и обзорные пиксели не переписываются из-за изменения фильтра отображения.

`Check overview quality` сравнивает тонкую кривую при 5% в окне 2537×2050 CSS-пикселей / DPR 2 с исходными тайлами и их GPU mipmaps. Проверяет LOD 3 и среднюю разницу каналов на линии менее 12/255. Лимит разрешения viewport в 8 мегапикселей по-прежнему применяется к обоим путям отрисовки.


## Частичная детализация и бюджет фоновой работы

`gpu/pageFallback.ts` разрезает область отсутствующей страницы по готовым дочерним страницам. Готовая деталь рисуется сразу, а оставшиеся участки используют соответствующие UV-фрагменты ближайшего резидентного родителя. Области не пересекаются. Один родитель может обслуживать несколько участков; увеличение числа участков не создаёт дополнительные GPU-текстуры. Пул остаётся ограниченным 256 слотами. При заполнении пула разрешено заменить ненужную для текущего LOD страницу, если её область покрывает актуальный закреплённый обзор.

`pageWork.ts` задаёт общий бюджет для фонового стриминга и подготовки обзора после завершения мазка. Окно длится 16 мс, CPU-бюджет составляет 4 мс, лимит операций — 64, загрузки — четыре страницы 258×258 RGBA за окно. Это окна планировщика, не измеренные кадры монитора. Проверки выполняются перед декодированием, downsample, упаковкой, копированием границ и загрузкой на GPU. Одна операция над тайлом может превысить мягкий CPU-бюджет; ожидание диска в него не входит. Одновременно подготавливаются не более двух страниц, включая явное обновление обзора. Холодный обход ключей пирамиды также уступает время обработке событий и не ставит всё дерево в очередь сразу.

Пропуски видимого покрытия получают приоритет перед дополнительной детализацией. Для общего обзора сохраняется резерв задания, чтобы длительное приближение не лишило следующий zoom-out готового изображения. Перед публикацией проверяются версия страницы и актуальность запроса. Таймер продолжения существует только при ожидающей работе. В Canvas wireframe видны число заданий, уступок планировщика и максимальный расход CPU/байтов в окне.

`Check partial refinement` на изолированной GPU-сцене проверяет готовую полосатую страницу рядом с грубым обзором, отрицательные координаты, UV-обрезку, границы квадрантов и alpha 50%. Затем дожидается детализации остальных участков и проверяет неизменность уже готовых пикселей. Unit-тесты проверяют отсутствие перекрытий, ограниченность геометрии, общий бюджет параллельных производителей и отмену устаревшей загрузки после ожидания.

## Активный мазок поверх резидентного обзора

Активный слой сохраняет отображение committed-части через virtual texture. Затем renderer записывает только `output` затронутых мазком тайлов в ту же временную поверхность слоя. Pipeline этих тайлов работает без blending: готовый output заменяет прежние пиксели, включая полностью прозрачный результат ластика. Opacity и blend слоя применяются после этой замены. Так `before` не смешивается второй раз, а ластик действительно открывает нижний слой.

Проверка полноты фонового покрытия использует число занятых листьев в sparse-индексе. Пустые части крупной страницы считаются прозрачными и не требуют текстур. Если актуального покрытия занятых участков ещё нет, активный слой временно использует исходный путь полного разрешения. В обычной worker-сессии общий обзор подготовлен при открытии документа и после завершения мазка.

Новые тайлы активного мазка рисуются независимо от committed-занятости. Cancel удаляет их вместе с preview. Commit передаёт результат существующему механизму сохранения и обновления обзора. Preview не записывается в постоянную пирамиду во время рисования; кисть по-прежнему растеризует исходное разрешение. Длинный мазок, затрагивающий много собственных тайлов, остаётся отдельным направлением оптимизации.

Тайлы активного мазка и страницы virtual texture используют линейную фильтрацию при увеличении. Иначе касание переключает существующий рисунок на `nearest`, а завершение мазка возвращает сглаживание. `Check stroke filtering` сравнивает GPU-кадры до касания с нулевым flow, во время него, после cancel и commit при увеличении 4×/16×/32×, повороте и DPR 1/2; допустимая разница — 2/255 на канал.

При завершении мазка `prepareOverview` обновляет также изменившиеся резидентные страницы, показанные в последнем кадре. Они используют прежние слоты атласа; неизменившиеся версии пропускаются. Это не позволяет следующему мазку показать грубый обзор на месте только что завершённой линии. GPU-проверка сразу начинает следующий мазок в соседнем тайле, без ожидания фонового уточнения, и проверяет сохранение пикселей после кисти и ластика. Повторная подготовка неизменившегося документа не загружает страницы заново.

В Canvas wireframe строка `Tile draws` показывает число отдельных тайлов активного мазка и committed-документа в последнем кадре. При прогретом обзоре маленький мазок на большом слое должен рисовать только свои тайлы; фон учитывается отдельно в page draws.

`Check active preview` создаёт два слоя по 256 тайлов, с прозрачностью и Multiply у активного слоя, и ограничивает scratch-кэш четырьмя тайлами. Локальный замер 2026-09-06: первый полный кадр после одного отпечатка сократился с 100.2 мс и 255 дополнительных чтений исходных тайлов до 1.8–2.4 мс и нуля таких чтений. Подготовка обзора выполнена до замера; это синтетический CPU+GPU-тест, не измерение задержки физического пера.

GPU-проверка сравнивает preview с исходным рендерером при прозрачной кисти, инкрементальном обновлении через границу тайла, полном стирании, pan/rotate/mirror/zoom, отмене после вытеснения scratch, commit, undo/redo и появлении новых ячеек вне рисунка. В прогоне активный результат совпал с эталоном в проверяемых областях; после перехода к committed-обзору максимальная разница составила 1/255 на канал. Проверка более дальнего zoom дополнительно требует нулевых чтений исходных тайлов при заполнении страницы преимущественно прозрачностью.

## Пакетная растеризация большой кисти

Рабочие текстуры, буферы и bind groups повторно используются после вытеснения содержимого тайла. Перед переназначением слота активные mask/output сохраняются существующим readback-механизмом. Новый пустой источник явно очищает output; восстановление активного тайла восстанавливает исходный base и mask. Свободные слоты включаются в число `residentTiles` и расход GPU-памяти, поэтому сохранение ресурсов для повторного использования не увеличивает заданный лимит. Reset и destroy освобождают и занятые, и свободные слоты.

`paint` объединяет независимые проходы до 32 тайлов в одну отправку GPU-команд. Очередь обязательно отправляется перед вытеснением/readback и перед повторной записью того же буфера отпечатков. При более чем 1024 отпечатках на тайл маска накапливается несколькими порциями, а output смешивается с исходными пикселями один раз после последней порции. `stampBounds.ts` ограничивает этот проход целочисленным прямоугольником изменённой области с запасом для antialiasing. Остальной output сохраняется через loadOp: load.

В локальном синтетическом прогоне кисти 512 px на 325 тайлах время обработки с ожиданием GPU уменьшилось со 172.6 до 130.8 мс. Новых текстур стало 384 вместо 975, отправок GPU-команд — 38 вместо 721. Рабочий пул ограничен 128 тайлами; 13 readback при вытеснении активных масок остаются. Это оптимизация полного разрешения, без изменения spacing, flow или алгоритма смешивания. Она не устраняет стоимость растеризации и сохранения новых исходных пикселей при очень длинном мазке.

`Check brush batching` сравнивает результат 2300 отпечатков с отправкой короткими порциями, затем сравнивает кэш на два слота с кэшем на 128 слотов при большой кисти, повторном посещении вытесненных участков, ластике и отмене. Все пиксели и прозрачные тайлы сравниваются побайтово. `Check 512px brush` дополнительно ограничивает число новых текстур и отправок команд, сохраняя проверки нулевого readback при показе активного мазка.

## Фоновое копирование вытесненных тайлов

`gpu/readbackQueue.ts` отправляет копирование mask/output в staging-буфер до повторного использования рабочих текстур. Кисть продолжает растеризацию, пока `mapAsync` возвращает предыдущую группу пикселей. Очередь ограничена двумя переиспользуемыми буферами: при стандартном scratch-кэше они занимают до 16 MiB, включённых в `gpuBytes`. Если оба заняты, следующий readback ждёт свободного места. Canvas wireframe показывает размер буферов, ожидающие копирования и число таких ожиданий.

Возврат к вытесненному тайлу, его отображение и завершение мазка дожидаются актуального снимка. После mapping пиксели упаковываются без потерь; плотные тайлы отдельно копируются из mapped-памяти перед unmap. Cancel и reset отменяют старые mappings, а проверки поколения не позволяют позднему результату перезаписать новый мазок или освободить уже переиспользуемый буфер. Ошибка актуального readback передаётся обработчику ошибки и отклоняет завершение мазка. Форматы документа и постоянного хранения не меняются.

Локальный синтетический прогон 2026-09-06: кисть 512 px на 325 тайлах обрабатывается за 87–89 мс вместо 130.8 мс, с ожиданием GPU. В повторном замере после обработки осталось ноль незавершённых readback; использованы два буфера, 16 MiB и десять ожиданий свободного места. Число readback осталось 13, новых текстур — 384, отправок команд — 38. Это перекрытие копирования с растеризацией, а не устранение их стоимости; заполненная очередь и повторное посещение ещё копируемого тайла по-прежнему требуют ожидания. Замер не измеряет задержку физического пера или FPS приложения.

`Check readback queue` искусственно задерживает ответы настоящего GPU. Проверяет работу при двух занятых буферах и ожидание третьего задания, возвращение к тайлу и его отображение, завершение мазка, отмену с немедленным повторным использованием буфера, ошибку mapping и уничтожение renderer с незавершённым ответом. Дополнительно проходят побайтовые проверки кисти/ластика с вытеснением, GPU-проверки preview и worker-проверки сохранения при заблокированном IndexedDB с последующим перезапуском.

## Solid 2 и Vite

Developer → **Web Worker + OffscreenCanvas** переключает способ выполнения. По умолчанию используется worker; отключение запускает тот же `paintRuntime.ts` на основном потоке с обычным `HTMLCanvasElement`. `mainThreadEndpoint.ts` загружает движок через динамический import только для этого режима и сохраняет изоляцию изменяемых данных клонированием сообщений. Локальный режим не создаёт Worker/OffscreenCanvas, PNG экспортируется через `HTMLCanvasElement.toBlob`.

Переключение отправляет `checkpoint`, временно блокирует команды редактирования и ждёт `checkpointed` после успешной записи IndexedDB. При ошибке страница остаётся открытой. После успеха открывается тот же URL с `?paintThread=main` или без этого параметра для worker. Документ и камера восстанавливаются; Undo и настройки сессии сбрасываются. Для сравнения задержки выставляйте одинаковые кисть, масштаб и настройки Developer. Проверка **Check execution modes** на QA-странице сравнивает документы побайтово в обоих направлениях и проверяет PNG обычного canvas.

Worker импортируется через `./paint.worker?worker`. Оба Vite-конфига, основной и standalone, задают ES-модули и отдельные экземпляры Solid/TypeGPU plugins для worker-сборки. Передача OffscreenCanvas и массивов сэмплов остаётся явным протоколом; замена конструктора на RPC primitive не заменяет сборку шейдерных модулей.

UI использует Solid 2 rc.4. Строки слоёв сохраняют DOM по `For keyed={(item) => item.id}`, поскольку каждое сообщение worker содержит новые объекты даже для неизменившихся слоёв. Значения строки читаются через accessor, чтобы обработчики использовали актуальную видимость и имя. Listener закрытия панели создаётся через совместимый `@solid-primitives/event-listener` на уровне компонента. Setup сессии возвращает teardown из `onSettled`; внутри такого callback нельзя создавать primitives, вызывающие `onCleanup`. Последовательность GPU-команд и сэмплы пера остаются вне реактивного графа.

`pnpm --filter @app-game/paint test:studio-ui` запускает DOM-проверки с браузерным runtime Solid 2 отдельно от node-тестов модели и worker. Проверка слоёв подтверждает сохранение фокуса при обновлении клонированных записей, идентичности кнопок при перестановке и актуальности callback-значений. Проверка puck подтверждает возврат фокуса канвасу после одноразового жеста; решение о закрытии возвращается из контроллера синхронно, без чтения ещё не обновлённого сигнала. `workerRecovery.test.ts` проверяет ошибки финальной растеризации и readback: неудавшийся preview сбрасывается, завершённые пиксели сохраняются, следующий мазок рисуется и проходит обычное автосохранение.
